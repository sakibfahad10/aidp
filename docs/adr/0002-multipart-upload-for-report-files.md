# Use multipart/form-data on a dedicated endpoint for report-file uploads

We accept uploaded medical-report files (PDF/JPEG/PNG, max 10 MB) as `multipart/form-data` on a new dedicated endpoint `POST /api/v1/predict/report-file`, instead of base64-encoding the file into the existing `POST /api/v1/predict` JSON body. The existing JSON endpoint — validated by the `predictRequestSchema` discriminated union over `symptom | structured | report` (text) — stays unchanged. multer's `memoryStorage` streams the file to Gemini's `inlineData` part and discards the buffer; only `{ reportType?, fileName, mimeType, fileSizeBytes }` is persisted.

The trade-off: this is a deliberate deviation from the "one JSON contract, polymorphism via a discriminated union" pattern we use for the other three input shapes. We accept it because the alternative — base64-in-JSON — would inflate payloads ~33%, force us to raise `express.json`'s body limit globally (impacting every endpoint), and conflate file-size limits with JSON-parser limits. A dedicated multipart route keeps the typed JSON contract pristine for the symptom/structured/text-report paths, lets multer enforce size and MIME-type limits before the body is buffered, and matches how browsers natively submit files. Shared validation rules (`ALLOWED_REPORT_FILE_MIME_TYPES`, `MAX_REPORT_FILE_SIZE_BYTES`, `isAllowedReportFile`) live in `packages/shared` so the multer `fileFilter` and the frontend's client-side check cannot drift.
